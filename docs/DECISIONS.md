# Implementation decisions

One line per non-obvious decision: what was chosen, why, what was tested. Design-level decisions live in DESIGN.md; this file records the implementer's deviations and findings.

- 2026-10-02 · Product name "Smidge" is the architect's proposal, not yet approved by Hunter. Code names use `cia`, the brand lives only in `packages/brand/brand.json`, so a rename touches one file plus repo names.
- 2026-10-02 · wasi-sdk 25 is expected at `/opt/wasi-sdk` (symlink on the dev VM). The spike that proved mozjpeg/libwebp/libdeflate/zstd compile for wasm32 with that sysroot plus `-D__wasi__` is recorded in `.cargo/config.toml`.
- 2026-10-02 · Toolchain pinned to 1.98.1 (the version on the dev VM and both lab VMs). Hunter's Windows PC has 1.92; rustup installs the pin on first build there.
- 2026-10-02 · Spike gate (DESIGN 2.5 item 4) passed on wasm32-unknown-unknown: `cia-wasm-spike` (cia-mozjpeg over mozjpeg-sys 2.2.3, cia-webp over libwebp-sys 0.14.4, wasm-bindgen 0.2.100) encodes a 640x480 JPEG and lossless/lossy WebP under Node 22; PIL decodes all three at the right size and the lossless WebP is pixel-exact. libc symbols the link needed from `cia-wasm-libc`: malloc, calloc, realloc, free, qsort (libwebp palette/Huffman sort), strlen, abort, exit, getenv, fprintf, fflush, fputs, fputc, fwrite, snprintf, stderr/stdout (mozjpeg jerror/jdatadst); memcpy/memset/memmove/memcmp were NOT needed (compiler-builtins provides them). libwebp-sys ≥0.14 defines WEBP_USE_THREAD under its `std` feature, which needs pthreads, so cia-webp enables `std` for non-wasm targets only. Module size: 715 KB from cargo, 691 KB after wasm-bindgen, 670 KB after `wasm-opt -O3`, 174 KB gzip -9. Debian's wasm-opt 108 additionally needs `--enable-sign-ext` (Rust 1.98 emits sign-extension ops by default); add it to the xtask flag list.
- 2026-10-02 · `cia-video-plan` aims at `Budget.raw_budget_bytes` (cia-core's `ResolvedLimit.budget_for(Video)`, limit minus `safety_bytes`, Discord Free 20,905,984). DESIGN 3.5.4 calls that number `hard_bytes` and subtracts one more byte (20,905,983); cia-core does not, so the planner follows cia-core. The worked example therefore gives total 2,191,133 bps instead of the design's 2,191,134 and a prediction of 19,238,810 bytes instead of 19,238,816; still "about 19.2 MB", still 720p30 Good.
- 2026-10-02 · Video overhead (3.5.2) is evaluated per rung with that rung's frame rate, since the formula needs an fps before a rung is chosen. The design's example uses 30 fps throughout, which is the chosen rung; the 60 fps start rung now pays for its own frames (95,796 bytes at 70 s instead of 66,396). Fractional frame rates round the per-second term up.
- 2026-10-02 · Refusal max-duration (3.5.5): the design's `min_bps = floor video + lowest audio rung` is unreachable under the 3.5.3 rule, which picks a higher audio rung once 15 percent of the total covers it (at the 360p floor the total is 547,840 bps and the rule picks 64 kb/s, not 32). The planner solves the bound against the audio rule that actually runs, iterates twice on the overhead as designed, then checks whole seconds against the real planner. Jayden's clip on Discord Free with NVENC gets max 4 min 37 s (277 s), not the design's 4 min 54 s; 294 s refuses because 64 kb/s audio leaves 452,707 bps for video, under the 483,840 floor. Tested: exactly max_duration_ms plans at 360p30, one second more refuses, for both margins.
- 2026-10-02 · `max_short_edge` (3.5.4 "drop rungs above it") is applied by scaling the start rung down to the cap at the start frame rate, not by deleting rungs. Deleting would lose 60 fps for every 1440p60 or 4K60 source on Discord (max 1080), since the 60 fps rung exists only at the start size. A 1440p60 clip for Discord now has 1080p60 first, then 1080p30, 720p30... WhatsApp (720, max_fps 30) gives 720p30, 540p30, 480p30, 360p30 as the design says.
- 2026-10-02 · Even dimensions follow FFmpeg's `scale=-2:H` exactly: `av_rescale(h, in_w, in_h * 2) * 2`, the nearest multiple of two from the real source aspect (854x480 -> 640x360, 2560x1080 -> 1706x720, 1081x1921 -> 480x852). The source size itself rounds down to even so no rung is larger than the source.
- 2026-10-02 · `keep_original_or_remux` always encodes a source with more than one audio track, even when it fits and its codecs are allowed: a copy or remux keeps both tracks and chat players play only the first, so the mix the user story expects ("both tracks audible") needs an encode.
- 2026-10-02 · `retry_scale` clamps the 3.5.8 factor to at most 1 and keeps the audio rung; the caller accepts an undershoot (below 85 percent of the budget) as is and never calls it. Moving "down one rung" continues down until a rung's floor is met, None when none remains.
- 2026-10-02 · The task brief quoted Jayden's clip as "2 min 4 s -> 720p, about 19.6 MB, Good"; DESIGN 1.3 and 3.5.4 say 1 min 10 s and 19.2 MB, and the 3.5.4 formula at 124 s gives 540p30, 19.2 MB, Okay (video 1,106,077 bps is 0.040 bpp at 720p, under the 0.050 floor). The 70 s design example is the required unit test; the 124 s case is asserted at what the formula produces.
- 2026-10-02 · Product key check character is Luhn mod 31 with the weighted sum reduced mod 31 instead of the textbook `a / N + a % N` fold. The fold is only a bijection for even N; with N = 31 it maps both 1 (B) and 16 (T) to 2, so a B/T typo in a doubled position would pass. Reducing mod the prime keeps weights 1 and 2 invertible: the exhaustive test (200 keys × 19 positions × 30 alternatives) and the adjacent-transposition test both pass, in Rust and TypeScript.
- 2026-10-02 · `cia-license` key `2026-10` is a PLACEHOLDER pair whose seed sits in `crates/cia-license/test-keys.json`. Before launch: `cargo xtask keygen`, paste the public key into `keys.rs`, set `LICENSE_SIGNING_KEY` on Vercel, delete the placeholder entry. The `test` kid is compiled in only under `cfg(test)` or feature `e2e`.
- 2026-10-02 · `device::device_hash()` falls back to hashing the hostname when no machine id can be read (no `/etc/machine-id`, broken registry) so activation never hard-fails; the raw id is still never sent. `machine_id()` is exposed separately and returns an error in that case.
- 2026-10-02 · `normalise` strips an explicit set (ASCII whitespace, NBSP, dash) rather than Rust `is_whitespace` / JS `\s`, which disagree on U+0085 and U+FEFF; both implementations share the list.
- 2026-10-02 · `@cia/api-types` verifies tokens with WebCrypto Ed25519 and falls back to `@noble/ed25519` (MIT) when `importKey("Ed25519")` rejects (Safari < 17). `signToken` (noble, server only) is byte-identical to Rust `token::sign`; the Vitest suite proves it by re-signing the shared vectors.
- 2026-10-02 · `cia-ffmpeg` maps filter-graph outputs by label (`-filter_complex "[0:v:0]…[v];[0:a:0]…[a]" -map [v] -map [a]`) instead of the 3.5.7 sketch's `-map 0:v:0 -map 0:a`, which with a `-filter_complex` would add the raw streams a second time. Stream selection (track N, mix of all tracks) lives in the graph inputs. `-v error` is added to the common prefix so stderr carries only what the failure message needs. VA-API gets `format=nv12,hwupload` on the chain and no `-pix_fmt yuv420p` (the upload decides the surface format). Snapshots in `crates/cia-ffmpeg/src/snapshots/` are the reference commands.
- 2026-10-02 · `is_vfr` (3.5.1 "2 percent spread in packet durations") also fires when the timestamp gaps vary by more than 2 percent, or when the declared packet duration disagrees with the actual spacing by more than 2 percent. The synthetic `v_vfr.mp4` has constant 1/60 s packet durations but frames 7/60 s apart (ffmpeg 5.1 muxes it that way), so the literal rule alone would call it CFR. Output is checked for CFR by probing the result (`avg_frame_rate == r_frame_rate`, no spread).
- 2026-10-02 · `fixtures/synth/v_rotated_90.mp4` is byte-identical to `v_720p_30fps_10s.mp4`: ffmpeg 5.1 has no `-display_rotation` and drops `-metadata:s:v rotate=90` when encoding from lavfi. The rotation test builds its own clip with `-c copy -metadata:s:v:0 rotate=90`, which does produce a display matrix (rotation 90, display 720x1280), then checks the encode comes out portrait with no rotation side data. `tools/fixtures/generate.py` should use `-c copy` for that fixture.
- 2026-10-02 · Trims use output-side `-ss START -to END` as 3.5.7 says. FFmpeg decodes and discards everything before START, so trimming the last minute of an hour-long 4K recording costs a full decode first; input-side `-ss` with the default `-accurate_seek` would be frame-accurate too when re-encoding. Left as designed; revisit if trim performance complaints appear.
- 2026-10-02 · The runner's 60 s watchdog counts progress blocks, not `out_time_us` advances, because a late trim legitimately produces blocks with `out_time_us=0` for a long time. The watchdog also applies after the last block while FFmpeg relocates the moov atom for `+faststart`; a multi-GB output on a slow disk could trip it.
- 2026-10-02 · `h264_mf` gets one `-hw_encoding 0` retry before being marked broken (3.5.7). A software encoder that exits non-zero or fails verification fails the item outright; only hardware encoders fall through to the next in the chain. Size retries (max 4) are counted separately from encoder failures.
- 2026-10-02 · `install::locate` never looks at `PATH`. The `CIA_FFMPEG` environment variable (path to an `ffmpeg` binary, `ffprobe` beside it) is the only override and exists for tests and CI; the integration tests additionally fall back to `/usr/bin/ffmpeg` and friends, in the tests only. `encoders.json` for a Smidge install sits in its version folder; for a user copy under `tools/ffmpeg/external/<hash of path+version>/`.
- 2026-10-02 · `pinned.rs` carries a PLACEHOLDER Ed25519 key whose seed is in `crates/cia-ffmpeg/test-keys.json` (kid `libraries-dev`), mirroring cia-license; the manifest URL points at a release tag that does not exist yet. Hash and signature verification, zip flattening, exec bits, staging-then-rename, the blocked-binary case and `remove` are covered by tests against a signed fake release over `file://` and over a `TcpListener` HTTP server with the real reqwest client.
- 2026-10-02 · Measured on this VM with Debian's ffmpeg 5.1.9 / libx264 two-pass: `v_720p_30fps_10s.mp4` to a 1,500,000-byte budget planned 960x540@30, video 1,014,019 bps + AAC 128 kb/s, predicted 1,440,520 bytes, produced 1,429,536 bytes (95.3 percent of budget, 0.8 percent under prediction) in one attempt.
